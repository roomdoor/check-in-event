# 승인 경로의 병목은 앱이다

`ceiling.env` 가 승인 경로의 천장을 찾았지만 어디가 막혔는지는 말하지 않았다.
후보가 앱과 Redis 둘이었고, 답에 따라 대응이 정반대다 — 앱이면 옆으로 늘리면
되고, Redis 면 Lua 가 단일 스레드라 늘려도 소용없다.

앱을 두 대로 늘려 재려면 인프라를 바꿔야 해서, 더 싼 실험 둘로 대신했다.

측정: 2026-09-22, AWS 3호스트. 앱 c7i.2xlarge(8 vCPU), MySQL+Redis
m7i.xlarge(4 vCPU), k6 c7i.2xlarge. `ap-northeast-2`.

## 실험 2 — Redis 단독 (결정적)

부하 호스트에서 `redis6-benchmark` 로 **앱과 같은 Lua 스크립트를 Redis 에
직접** 쏘았다. 커넥션 50개, 파이프라이닝 없음. `__rand_int__` 로 userId 를
매번 다르게 줘서 중복 조기반환이 아니라 승인 전체 경로를 타게 했다
(300,000회 중 259,293개가 새 유저였다 — 100만 공간에서 뽑을 때의 기댓값과
맞는다).

| | 초당 | p95 |
| --- | --- | --- |
| PING (이 경로의 바닥값) | 163,399 | 0.41ms |
| **같은 Lua 스크립트** | **54,955** | 1.13ms |
| 앱을 거친 같은 일 | 3,016 ~ 4,672 | — |

**Redis 는 이 스크립트를 초당 5만 5천 건 처리한다. 앱을 거치면 3천~4천 7백이다
— 12~18배 차이다.** Redis 는 실제 부하에서 자기 용량의 10%도 안 쓰고 있었다.

지연도 같은 곳을 가리킨다. Redis 는 p95 1.13ms 에 답하는데 앱은 낮은 부하에서도
p95 4.3~5ms 다. **3~4ms 가 앱에서 쓰인다.**

Lua 가 PING 의 1/3 인 것은 명령 6개짜리 스크립트로서 자연스럽다. 병목의
징후가 아니다.

## 실험 1 — CPU 분담 (보조, 단독으로는 결론 못 냄)

`ceiling.env` 4회차를 다시 돌리면서 양쪽 호스트 CPU 를 1초 간격으로 찍었다.
분 단위 평균(사용률 = 100 − idle):

| 시각 | 회차 | SUT (앱, 8 vCPU) | support (MySQL+Redis, 4 vCPU) |
| --- | --- | --- | --- |
| 07:37 | 800 | 11% | 9% |
| 07:38 | 1600 | 21% | 13% |
| 07:39 | 3200 | 27% | 21% |
| 07:40 | 6400 | **31%** | 28% |
| 07:41 | 드레인 | 21% | **37%** |

**어느 쪽도 포화가 아니다.** 다만 이것만으로는 결론을 못 낸다 — 호스트 전체
평균이라 **단일 스레드 병목이 안 보인다.** Redis 는 싱글 스레드이므로 4 vCPU
호스트에서 코어 하나가 100% 여도 호스트는 25% 로 찍힌다. support 의 28~37%
안에 그게 숨어 있을 수 있었다.

실험 2 가 그 가능성을 지웠다. Redis 가 초당 5만 5천을 하는데 부하 때는 3천~4천을
받았으니, 코어가 꽉 찼을 리 없다.

## 덤 — 포화 지점은 재현이 안 된다

같은 `ceiling.env` 를 두 번 돌린 결과다.

| rate | 1차 저장 | 2차 저장 | 차이 |
| --- | --- | --- | --- |
| 800 | 43,372 | 43,547 | 0.4% |
| 1600 | 86,711 | 86,603 | 0.1% |
| 3200 | 171,499 | 171,983 | 0.3% |
| **6400** | **180,998** | **280,329** | **55%** |

포화 아래에서는 0.5% 안에 든다. 포화 지점에서만 55% 벌어진다. **그러므로
"천장은 초당 3,000건" 이라고 말하면 안 된다** — 그 수치는 n=1 이고, 두 번째
회차는 초당 4,672건이었다. 확실한 건 3200 RPS(초당 2,858건)까지는 도착률을
그대로 따라간다는 것까지다.

## 그래서 무엇을 하면 되나

앱이 병목이므로 **앱을 옆으로 늘리는 게 통한다.** 승인 판정이 Redis 에 있어
앱은 상태가 없다. Redis 에 12~18배 여유가 있으니 앱을 여러 대 붙여도 한동안
그쪽이 벽이 되지 않는다.

앱의 어느 부분인지는 아직 모른다. CPU 가 31% 인데 못 받는 것은 스레드나 대기가
막고 있다는 뜻이다 — Tomcat 워커, 커넥션 풀, JVM 중 하나다. 그건 다음에 잰다.
