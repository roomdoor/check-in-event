# 승인 경로의 병목을 찾다가, 병목이 없다는 걸 알게 된 기록

> **이 회차들은 콜드 JVM 이다.** 아래 "앱을 거친" 수치는 승인 경로의 능력이
> 아니라 갓 뜬 JVM 이 낸 값이다. 결론은 README 5 장에서 뒤집혔다 — 데워진 앱은
> 6,400 RPS 를 p95 2.15ms 에 받는다. 이 문서는 그 과정의 근거로 남긴다.

`ceiling.env` 가 승인 경로의 한계처럼 보이는 지점을 찾았지만 어디가 막혔는지는
말하지 않았다. 후보가 앱과 Redis 둘이었고, 답에 따라 대응이 정반대다 — 앱이면
옆으로 늘리면 되고, Redis 면 Lua 가 단일 스레드라 늘려도 소용없다.

앱을 두 대로 늘려 재려면 인프라를 바꿔야 해서, 더 싼 실험 둘로 대신했다.

측정: 2026-09-22, AWS 3호스트. 앱 c7i.2xlarge(8 vCPU), MySQL+Redis
m7i.xlarge(4 vCPU), k6 c7i.2xlarge. `ap-northeast-2`.

## 실험 1 — Redis 단독

부하 호스트에서 `redis6-benchmark` 로 **앱과 같은 Lua 스크립트를 Redis 에
직접** 쏘았다. 커넥션 50개, 파이프라이닝 없음. `__rand_int__` 로 userId 를
매번 다르게 줘서 중복 조기반환이 아니라 승인 전체 경로를 타게 했다
(300,000회 중 259,293개가 새 유저였다 — 100만 공간에서 뽑을 때의 기댓값과
맞는다).

| | 초당 | p95 |
| --- | --- | --- |
| PING (이 경로의 바닥값) | 163,399 | 0.41ms |
| **같은 Lua 스크립트** | **54,955** | 1.13ms |

**Redis 는 이 스크립트를 초당 5만 5천 건 처리한다.** 실제 부하에서 통과한 양은
그 10% 아래였다. Lua 가 PING 의 1/3 인 것은 명령 6개짜리 스크립트로서
자연스럽고, 병목의 징후가 아니다.

**이 결론은 지금도 유효하다.** 데워진 앱이 낸 5,761/s 로 비교해도 Redis 는
자기 용량의 10%만 쓴다.

## 실험 2 — CPU 분담

`ceiling.env` 4회차를 다시 돌리면서 양쪽 호스트 CPU 를 1초 간격으로 찍었다.
분 단위 평균(사용률 = 100 − idle):

| 시각 | 회차 | SUT (앱, 8 vCPU) | support (MySQL+Redis, 4 vCPU) |
| --- | --- | --- | --- |
| 07:37 | 800 | 11% | 9% |
| 07:38 | 1600 | 21% | 13% |
| 07:39 | 3200 | 27% | 21% |
| 07:40 | 6400 | **31%** | 28% |
| 07:41 | 드레인 | 21% | **37%** |

**어느 쪽도 포화가 아니다.** 다만 이것만으로는 결론을 못 낸다 — 호스트 전체
평균이라 **단일 스레드 병목이 안 보인다.** Redis 는 싱글 스레드이므로 4 vCPU
호스트에서 코어 하나가 100% 여도 호스트는 25% 로 찍힌다.

실험 1 이 그 가능성을 지웠다.

## 실험 3 — 스레드 덤프

부하 중에 `kill -3` 으로 JVM 스레드 덤프를 떴다.

| | |
| --- | --- |
| Tomcat 워커 | 200개 중 **196개가 유휴** (`TaskQueue.poll` 에서 대기) |
| Redis 응답 대기 중인 워커 | 400 샘플 중 **1개** |
| Lettuce 이벤트루프 | 133초 중 CPU 7.6초 = 코어의 **5.7%**, `EPoll.wait` 에서 대기 |

**앱도 놀고 있었다.** Tomcat 워커 수도, Lettuce 단일 커넥션도 아니었다 —
둘 다 이 덤프 전에 세운 가설이고 둘 다 틀렸다.

## 여기서 막혔고, 그게 답이었다

Redis 도 아니고 앱도 아니고 CPU 도 아닌데 p95 가 990ms 였다. **전부 한가한데
응답이 1초 걸린다**는 모순이 남았다.

답은 "무엇이 막는가"가 아니라 "무엇을 재고 있었는가" 였다. 스윕이 회차마다
앱을 재기동하므로 **매 회차가 갓 뜬 JVM 을 재고 있었다.** 응답이 밀리초
단위인 서비스에서는 JIT 컴파일과 클래스 로딩 비용이 측정값보다 크다.

같은 앱, 같은 6,400 RPS:

| 앱 상태 | p95 | 버려진 요청 |
| --- | --- | --- |
| 따뜻함 | **2.15ms** | 0 |
| 재기동 직후 | **1,474ms** | 10,562 |

**686배.** 자세한 건 README 5 장과 `loadtest/results/ec2/warmup`.

## 남은 것

- **승인 경로의 천장은 아직 못 찾았다.** 6,400 RPS 에서도 여유가 있다
- **앱 여러 대는 안 재봤다.** 지금은 급하지 않다 — 늘려야 할 이유가 아직 없다
- **처음 밀린 건 드레이너다.** batch 1600 / delay 100ms 에서 초당 4,165건.
  더 짧은 회차는 안 밀려서 5,425건 이상이라는 하한만 준다 — 종류가 다른 값이다
